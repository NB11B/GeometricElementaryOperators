## CUDA Toolkit 13.0 on Windows

Run from a Developer PowerShell for Visual Studio with CMake, Ninja, CUDA Toolkit 13.0, a compatible NVIDIA driver, and Compute Sanitizer on `PATH`.

```powershell
$ErrorActionPreference = 'Stop'

New-Item -ItemType Directory -Force local-evidence | Out-Null
git rev-parse HEAD | Tee-Object local-evidence\commit.txt
git status --short | Tee-Object local-evidence\status.txt
nvcc --version | Tee-Object local-evidence\nvcc-version.txt
nvidia-smi | Tee-Object local-evidence\nvidia-smi.txt
compute-sanitizer --version | Tee-Object local-evidence\compute-sanitizer-version.txt

foreach ($precision in @('float', 'double')) {
    $useDouble = if ($precision -eq 'double') { 'ON' } else { 'OFF' }
    $build = "build-cuda-$precision"

    Remove-Item -Recurse -Force $build -ErrorAction SilentlyContinue
    cmake -S . -B $build -G Ninja `
      -DCMAKE_BUILD_TYPE=Release `
      -DGEO_BUILD_CUDA=ON `
      -DGEO_BUILD_TESTS=ON `
      -DGEO_BUILD_BENCHMARKS=ON `
      -DGEO_USE_DOUBLE=$useDouble `
      -DCMAKE_CUDA_ARCHITECTURES=native `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-configure.log"

    cmake --build $build --parallel `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-build.log"

    cmake --build $build --target generate_cuda_schedules `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-schedules.log"

    ctest --test-dir $build --output-on-failure `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-ctest.log"

    compute-sanitizer --tool memcheck "$build\test_cuda.exe" `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-api-memcheck.log"
    compute-sanitizer --tool racecheck "$build\test_cuda.exe" `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-api-racecheck.log"
    compute-sanitizer --tool memcheck "$build\test_cuda_schedules.exe" `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-schedule-memcheck.log"
    compute-sanitizer --tool racecheck "$build\test_cuda_schedules.exe" `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-schedule-racecheck.log"

    foreach ($batch in @(1, 32, 256, 1024, 16384, 262144, 1048576)) {
        & "$build\bench_cuda.exe" `
          --device 0 `
          --batch $batch `
          --iterations 100 `
          --warmup 10 `
          --operation all `
          --csv "local-evidence\cuda-$precision-batch-$batch.csv" `
          2>&1 | Tee-Object "local-evidence\cuda-$precision-batch-$batch.log"
        if ($LASTEXITCODE -ne 0) {
            throw "CUDA benchmark failed for $precision batch $batch"
        }
    }

    cmake --build $build --target workload_report `
      2>&1 | Tee-Object "local-evidence\cuda-$precision-workload-report.log"
}
```

The device evidence is acceptable only when both precisions compile, all three CUDA CTests execute rather than skip, both public-API and generated-schedule Compute Sanitizer runs pass, and every benchmark row reports zero mismatches.

The CUDA harness records canonical operation names:

- `addition`
- `geometric_product`
- `reverse`
- `vector_dot`
- `vector_wedge`
- `rotor_action`

It also records operation-specific uploaded and downloaded byte counts, logical kernel bytes, upload/kernel/download/total time, throughput, logical kernel bandwidth, transfer bandwidth, and numerical error.

Capture the application’s `GEO_DEVICE`, `GEO_CHECKS`, `GEO_RESULT`, memory-report, and heap-soak records. A compile-only build is not physical-device timing or correctness evidence.

## Fixed C and RTL equivalence

```sh
set -euo pipefail

python3 tools/generate_rtl.py \
  --out-dir build-rtl \
  --schedule-json rtl/examples/rotor_action_schedule.json \
  --self-test
python3 tools/generate_rtl_schedule.py \
  --out-dir build-rtl \
  --self-test \
  --schedule-json rtl/examples/addition_schedule.json \
  --schedule-json rtl/examples/geometric_product_schedule.json \
  --schedule-json rtl/examples/vector_dot_schedule.json \
  --schedule-json rtl/examples/vector_wedge_schedule.json \
  --schedule-json rtl/examples/rotor_action_schedule.json

for source in build-rtl/test_geo_schedule_*.c; do
  name="$(basename "$source" .c)"
  clang -std=c11 -Wall -Wextra -Wpedantic -Wconversion \
    -Iinclude "$source" src/fixed.c -lm -o "build-rtl/$name"
  "build-rtl/$name"
done

iverilog -g2012 -s tb_geo_cl20_product_q \
  -o build-rtl/cl20_tb.vvp \
  build-rtl/geo_cl20_product_q.sv build-rtl/tb_geo_cl20_product_q.sv
vvp build-rtl/cl20_tb.vvp

for module_file in build-rtl/geo_schedule_*.sv; do
  module="$(basename "$module_file" .sv)"
  testbench="tb_${module}"
  iverilog -g2012 -s "$testbench" -o "build-rtl/${module}.vvp" \
    build-rtl/geo_cl20_product_q.sv "$module_file" "build-rtl/${testbench}.sv"
  vvp "build-rtl/${module}.vvp"
  yosys -p "read_verilog -sv build-rtl/geo_cl20_product_q.sv $module_file; synth -top $module; stat"
done

iverilog -g2012 -s tb_geo_program_controller \
  -o build-rtl/controller_tb.vvp \
  build-rtl/geo_program_controller.sv build-rtl/tb_geo_program_controller.sv
vvp build-rtl/controller_tb.vvp
yosys -p 'read_verilog -sv build-rtl/geo_program_controller.sv; synth -top geo_program_controller; stat'
```

The product and schedule fixtures must cover nominal behavior, rounded-multiplication overflow, final-wide-sum overflow, and cancellation accepted by fixed C. The controller simulation must cover successful completion, sticky overflow abort, dependency blocking, restart clearing, one-cycle `done`, and success-only `result_valid`.
