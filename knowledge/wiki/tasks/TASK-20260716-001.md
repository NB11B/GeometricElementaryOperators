# TASK-20260716-001 — Complete v0.19 kernel backends and CUDA harness

## Original request

Build and test the rest of the kernel, including the CUDA 13 batched harness,
and save independently reviewed checkpoints to GitHub without masking the
unmerged v0.18.2 release gate.

## Objective

Audit the current v0.19 integration head, complete the CUDA harness and the
remaining backend-equivalence and embedded work, run the unified validation
matrix, independently review each bounded stage, and publish verified branch
checkpoints while keeping v0.18.2 release status explicit.

## Initial constraints

- Preserve unrelated working-tree changes.
- Keep CUDA/v0.19 work isolated from the v0.18.2 release hotfix.
- Do not merge or tag v0.18.2 until an exact-head GitHub Actions run actually
  starts and passes.
- Do not claim Compute Sanitizer coverage unless the tool attaches and reports
  a successful run.
- Do not mark conclusions verified before evidence is collected.

## Expected deliverables

- A hardened CUDA 13 public and generated-schedule harness.
- A truthful unified workload/error benchmark contract.
- Deterministic randomized all-36 fixed-point typed numerical-envelope
  validation at representative Q-formats.
- Shared-vector, bit-for-bit C/SystemVerilog schedule equivalence with checked
  overflow behavior.
- ESP32-S3 application and the strongest available build/hardware evidence.
- Independently reviewed, knowledge-backed GitHub branch checkpoints.

## Plan

The work is staged to keep review and checkpoints bounded:

1. **Stage 1 — baseline and generated CUDA safety:** repair the stale safety
   test and inherited RTL-generator defects; validate generated CUDA launch
   geometry against the active device; state public/generated vector-wedge
   contracts explicitly; add real-GPU and generator regressions; run portable,
   CUDA, and generator matrices; obtain independent review.
2. **Stage 2 — workload contract:** make the workload reporter exercise and
   label the actual public/generated paths, forward deterministic seeds, add a
   require-CUDA mode, and produce a complete operation-by-backend manifest.
3. **Stage 3 — fixed point:** add randomized typed numerical-envelope coverage
   for all 36 targets at representative Q-formats.
4. **Stage 4 — RTL equivalence:** establish the shared-vector C/fixed/RTL
   corpus, multi-Q comparisons, checked intermediate overflow cases, and
   controller/datapath validation.
5. **Stage 5 — ESP32 and release integration:** validate the ESP32-S3 app at
   the strongest available level, run the full matrix, independently review,
   and publish checkpoints without merging or tagging prematurely.

Stage 1 non-goals were benchmark redesign, all-36 fixed-point expansion,
shared-vector RTL equivalence, physical ESP32 execution, v0.18.2 release
acceptance, rebasing, merging, and tagging.

Stage 2 non-goals were all-36 fixed-point expansion, shared-vector RTL
equivalence, physical ESP32 execution, hosted-CI remediation, successful
Compute Sanitizer attachment, rebasing, merging, and tagging.

Stage 3 non-goals were a wholly independent floating oracle, shared-vector RTL
equivalence, physical ESP32 execution, hosted-CI remediation, successful
Compute Sanitizer attachment, rebasing, merging, and tagging.

## Acceptance criteria

Stage 1 required:

- removal of the obsolete safety-test field write;
- preservation of generated-launcher zero-count, null-pointer, arithmetic-
  overflow, and CUDA error-propagation behavior;
- active-device validation of thread-block and x-grid limits;
- safe real-GPU rejection regressions with no accidental oversized launch;
- truthful distinction between the scalar public wedge API and the full-blade
  generated schedule result;
- full identifier matching and valid generated C string escaping in the RTL
  schedule generator;
- GCC and Clang Release float/double matrices, CUDA Release float/double tests
  on a real GPU, and the full generator suite;
- independent review with no unresolved BLOCKER or HIGH finding.

Stage 2 required:

- execution of the six public CUDA batched APIs and five available generated
  CUDA schedule launchers, with no benchmark-private substitute kernels;
- exact 27-row CPU and 11-row CUDA operation/backend/timing-scope manifests;
- deterministic seed forwarding and exact precision/iteration/warmup/seed/
  batch configuration validation;
- required-CUDA failure semantics while retaining optional CPU-only mode;
- truthful `host_end_to_end` public and `device_kernel` generated timing
  scopes;
- checked and operation-specific upload, download, and logical byte counts;
- lazy generated resources so reverse-only public execution stays independent
  of the generated schedule path;
- contract regressions, portable and real-GPU validation in float and double,
  and independent review with no unresolved material finding.

Stage 3 required:

- a CMake cache contract for signed 32-bit Q formats with 1 through 30
  fractional bits, propagated to the kernel and its consumers;
- transactional `geo_fixed_geb36_execute` failure behavior and initialized
  working values so invalid targets, arithmetic failure, and null output do not
  expose partial results or undefined local state;
- an exact manifest of all 36 target names and expected typed result kinds;
- deterministic fixtures constructed directly in raw Q-format, with the
  floating reference evaluated on values decoded from those same fixtures;
- Q-aware fixture ranges, including a non-degenerate Q1 path, and a 64-fixture
  requested-seed diversity preflight covering both signs, distinct operands,
  mixed-sign multivectors, and nonparallel vectors;
- double-precision projective normalization, explicit per-operation LSB error
  budgets, and double reference precision for the Q30 LSB envelope;
- strict report validation of the exact manifest, executable-reported
  precision/Q/sample/seed configuration, result kinds, accounting, finite
  metrics, completion, and zero failure counts;
- ASan/UBSan validation at Q1, Q8, Q16, Q24, and Q30, native MSVC float and
  double validation, and independent review with no unresolved material
  finding.

The complete task remains open until Stages 4–5 and final publication gates are
finished.

## Implementation

Stage 1 changed the smallest relevant surfaces:

- Removed the stale optimizer ABI field assignment from the safety regression.
- Generated CUDA launchers now query the active device and its properties,
  propagate query failures unchanged, and reject a block or x-grid dimension
  that exceeds the reported device limit.
- Added real-GPU regressions for excessive block and grid geometry, followed by
  synchronization to detect an accidental launch.
- Documented the public scalar e12-coefficient wedge result and the generated
  full Cl(2,0) wedge-root result.
- Repaired the inherited RTL generated-C newline and changed identifier checks
  to `fullmatch`, with self-test and CLI regressions for trailing junk.

Stage 2 completed the workload contract:

- Replaced benchmark-private CUDA kernels with the six public batched APIs and
  the five generated schedule launchers that actually exist.
- Added exact CPU and CUDA capability manifests, duplicate/omission/extra-row
  rejection, deterministic seed forwarding, exact run-configuration checks,
  required-CUDA semantics, and mismatch rejection.
- Labeled public API timings as `host_end_to_end` and generated schedule
  timings as `device_kernel`, and documented what each clock includes.
- Added overflow-safe, operation-specific transfer and logical byte accounting,
  including scalar public dot/wedge results and the generated rotor's third
  input.
- Allocated generated resources only for selected generated operations and the
  reverse buffer only for generated rotor action; added a reverse-only real-GPU
  smoke test.
- Added focused Python contract tests and updated the visible benchmark and
  validation documentation.

Stage 3 completed the fixed GEB-36 typed numerical envelope:

- Added the validated `GEO_FIXED_FRACTION_BITS` CMake cache setting and made
  its value a public kernel compile definition.
- Initialized fixed executor working locals and extended safety tests to prove
  that invalid targets, overflow paths, and null output are rejected without
  mutating caller output.
- Replaced the selected-operation numerical harness with the frozen 36-target
  name/kind manifest: 26 Cl(2,0), five scalar, four projective, and one
  unipotent result.
- Constructed deterministic fixtures in raw Q-format, decoded those exact
  inputs for the floating GEB reference, normalized projective results in
  double precision, and applied explicit operation-specific budgets from zero
  to 48 LSBs.
- Added Q1-aware sign and magnitude generation plus a requested-seed
  64-fixture diversity preflight to prevent a superficially passing but
  degenerate corpus.
- Hardened the reporter to reject precision/Q/sample/seed disagreement,
  missing, extra, duplicate, or mistyped rows, incomplete accounting,
  non-finite metrics, overflow, status/kind failures, and numerical
  mismatches.
- Added the Python reporter contract suite and a permanent five-Q
  Clang ASan/UBSan CI matrix. The CI harness compiles the floating reference as
  double so Q30 has enough resolution for an LSB-scaled envelope.

## Decisions made

- Generated launch geometry is checked against the active device rather than a
  CUDA architectural constant.
- A zero-count generated launch remains a successful no-op before pointer or
  device-property queries.
- Public vector wedge and generated vector-wedge schedule outputs remain
  intentionally different and are documented at their respective interfaces.
- The v0.19 checkpoint remains release-isolated: `origin/main` contains the
  PR #13 merge `0280f0d`, but hosted exact-head validation and a v0.18.2 tag
  remain outstanding, and provenance commit `4469433` is not an ancestor.
- Workload capabilities are an exact version-controlled contract. Missing,
  extra, or duplicate paths fail reporting instead of silently changing
  coverage.
- Public CUDA API and generated schedule timings remain separate because their
  measurement scopes are materially different; generated reverse is not
  claimed.
- The fixed GEB-36 numerical envelope is an exact typed capability contract:
  every target and requested sample must complete, and incomplete or permissive
  reporting is a failure.
- Numerical expectations are evaluated on decoded raw-Q fixtures rather than
  pre-quantization floating values. LSB budgets are operation-specific, and
  the Q30 envelope intentionally uses a double floating reference.
- Compiled precision and Q format are evidence reported by the executable and
  must match the reporter request; command-line metadata alone is not trusted.
