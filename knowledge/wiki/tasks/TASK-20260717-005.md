# TASK-20260717-005 — Generate ESP32 IMU sparse schedules automatically

## Objective

Replace the manually frozen A1/B1 polynomial helpers with deterministic C generated from a checked schedule intermediate representation.

## Initial scope

The first schedule IR covers the two sparse kernels responsible for the principal fusion result:

- quaternion gravity projection;
- quaternion multiplied by a pure-vector angular-rate quaternion.

The IR records named inputs, named outputs, integer coefficients, and two-factor product terms. The generator validates identifiers, uniqueness, factor references, coefficient constraints, and deterministic ordering before emitting:

- floating C helpers;
- Q32 integer accumulator helpers.

## Implemented

- Added `imu_orientation_sparse_v1.json`.
- Added deterministic generator `generate_imu_sparse_schedule.py`.
- Added checked-in generated header `geo_imu_generated_schedule.h`.
- Added equivalence tests over deterministic floating and integer corpora.
- Added invalid-schedule rejection tests.
- Added generator staleness checking to the dedicated ESP32 workflow.
- Added the generator and test gates to the build-only and full evidence runners.
- Included and exercised generated floating and Q32 helpers in the firmware startup self-test.

## Acceptance criteria

- generator output is byte-for-byte deterministic;
- checked-in generated header passes `--check`;
- float IR evaluation matches direct formulas over at least 1,000 deterministic samples;
- integer accumulator evaluation matches direct formulas exactly over at least 1,000 deterministic samples;
- invalid zero coefficients and unknown factors are rejected;
- generated helpers compile in the ESP32 firmware and pass the startup formula checks;
- generated helpers replace the manually written A1/B1 sparse helper bodies;
- generated A1 output hash equals manual A1 and C;
- generated B1 output hash equals manual B1;
- generated latency remains within 1% of the manual fused schedule on the same board and measurement contract.

## Current boundary

The generator, IR, generated header, host equivalence tests, workflow gate, evidence-runner gate, and on-device startup checks are present. Runtime replacement of the manually written A1/B1 helper bodies is the remaining implementation step before physical hash and timing comparison.

## Unresolved questions

- Should the IR remain polynomial-only or be generalized immediately to typed expression DAGs?
- How should per-intermediate Q formats and overflow envelopes be represented?
- Should common-subexpression elimination occur before or after backend-specific accumulator formation?
- Can the same schedule IR emit scalar C, ESP32-S3 SIMD, CUDA, and RTL without changing task semantics?
