# TASK-20260717-006 — Carry the IMU fusion benchmark onto CUDA

## Objective

Reproduce the deterministic IMU benchmark contract on an NVIDIA GPU while preserving the sequential recurrence inside each trajectory and exposing useful parallelism across independent trajectories.

## Measurement distinction

A single 200 Hz filter stream is a latency control, not the primary GPU workload. The GPU benchmark must report separately:

- resident replay throughput, where one thread processes one complete trajectory;
- streaming-step latency, where each kernel advances a batch by one sample;
- end-to-end latency including transfers;
- future CUDA Graph and persistent-kernel variants.

Kernel-only results must never be presented as end-to-end system latency.

## Required six-way target

- A0 generic GEO float;
- B0 generic GEO Q16;
- A1 generated sparse GEO float;
- B1 generated sparse GEO Q16;
- C conventional quaternion;
- D quantized TinyML fixture.

## Initial implementation

- Added a CUDA emitter for the same checked IMU schedule IR used by the ESP32 compiler branch.
- Added checked-in generated CUDA float and Q32 helpers.
- Added deterministic generator staleness tests.
- Added a standalone CUDA benchmark for resident-replay A1 versus C.
- Added alternating implementation order across measured runs.
- Added device metadata, kernel timing, throughput, accuracy, NaN, trace-hash, batch-hash, state-size, and device-allocation reporting.
- Added a PowerShell runner that captures exact commit, GPU identity, CUDA compiler, generator gates, build logs, batch-matrix output, and SHA-256 evidence manifest.

## GPU benchmark contract

- 12,000 samples per trajectory;
- 200 Hz logical trace;
- 30 measured runs;
- batch matrix beginning with 1, 32, 256, 1,024, and 4,096 trajectories;
- one captured validation trajectory outside the timed region;
- CUDA-event kernel timing;
- exact same-device hash plus later canonical semantic hash for cross-architecture comparison;
- precise division/square-root and FMA-disabled parity build;
- performance build reported separately when FMA is enabled.

## Acceptance stages

### G0

Generated floating A1 and conventional C compile and execute. Their same-build trace hashes, displayed accuracy, and NaN counts agree. Hashes remain stable over 30 runs.

### G1

Generated B1 Q16 executes with zero arithmetic failures and remains inside the established fixed-path error envelope.

### G2

A0/B0/A1/B1/C/D execute the same resident, streaming, and end-to-end contracts across the batch matrix.

### G3

The shared schedule IR emits both ESP32 scalar and CUDA device helpers. Generated CUDA A1/B1 remain within 1% of manually specialized CUDA references at useful batch sizes.

## Current boundary

Only resident-replay A1 and C are wired into the first executable. The code has not yet been compiled or run on the physical GPU. B1, generic A0/B0, D, streaming-step, end-to-end, CUDA Graph, and persistent-kernel modes remain pending.

## Unresolved questions

- At what batch size does GPU resident replay outperform CPU execution end to end?
- Does disabling FMA preserve exact A1/C device-hash equality on the RTX 5070 Laptop GPU?
- What launch topology is best for the streaming-step test?
- Should replay samples remain in global memory, constant memory, or texture/read-only cache?
- How much throughput is lost when every trajectory uses a distinct replay or state perturbation?
- Can B1 use per-intermediate Q formats without increasing register pressure enough to reduce occupancy?
- Should D use cuBLASLt, custom int8 kernels, or both as separate baselines?
